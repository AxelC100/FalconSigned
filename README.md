# 🔐 FalconSigned

**Secure Academic Document Signing & Verification System**

FalconSigned is an **academic cybersecurity project and proof of concept (PoC)** developed to explore the secure signing, encryption, verification, and management of academic documents.

The application demonstrates how cryptographic mechanisms, multi-factor authentication, role-based access control, key lifecycle management, and security auditing can be combined to protect digital academic documents against unauthorized modification and forgery.

> **Academic Project:** FalconSigned was developed for educational purposes as part of a university cybersecurity project. It is not intended to replace certified digital signature solutions, Public Key Infrastructure (PKI), or legally recognized digital signature systems.

---

## 🎯 Project Objective

The main objective of FalconSigned is to provide a prototype capable of securely signing and verifying academic PDF documents.

The system is designed to:

- Verify document integrity.
- Detect unauthorized modifications.
- Authenticate users before allowing sensitive operations.
- Digitally sign documents using asymmetric cryptography.
- Encrypt stored documents.
- Protect sensitive student information.
- Manage cryptographic key rotation and revocation.
- Maintain security audit records.
- Apply Role-Based Access Control (RBAC).
- Separate administrative and auditing responsibilities.

---

## 🛡️ Security Features

FalconSigned implements multiple security mechanisms:

### Digital Signatures

Documents are digitally signed using:

- **RSA 2048-bit keys**
- **RSA-PSS**
- **SHA-256**

The SHA-256 hash of the PDF is digitally signed with the active RSA private key.

During verification, FalconSigned recalculates the document hash and verifies the RSA-PSS signature using the corresponding public key.

---

### Document Integrity

FalconSigned calculates a **SHA-256 hash** for every registered document.

If the document is modified after being signed, even slightly, the calculated hash will differ from the stored value and the application will display an integrity warning.

---

### Hybrid Document Encryption

Stored documents are protected using hybrid encryption.

The process combines:

- **AES-256-GCM** for document encryption.
- **RSA-OAEP** for protecting the AES encryption key.

Process:

```text
PDF Document
     │
     ▼
AES-256-GCM
     │
     ▼
Encrypted Document (.enc)

AES Key
     │
     ▼
RSA-OAEP
     │
     ▼
Protected AES Key
```

This allows FalconSigned to efficiently encrypt complete PDF documents while protecting the symmetric encryption key using asymmetric cryptography.

---

### Sensitive Data Protection

Sensitive document metadata such as:

- Student name
- Student ID
- Document type

is encrypted before being stored in the SQLite database.

FalconSigned uses **Fernet authenticated symmetric encryption** for this purpose.

---

### Password Security

Passwords are never stored in plaintext.

FalconSigned uses:

- **PBKDF2-HMAC-SHA256**
- Random salts
- 300,000 iterations

to derive and store password hashes.

---

### Multi-Factor Authentication

User authentication requires:

1. Username
2. Password
3. Six-digit TOTP code

FalconSigned implements **Time-Based One-Time Passwords (TOTP)** compatible with authenticator applications such as Google Authenticator.

TOTP codes change every 30 seconds.

---

### Brute-Force Protection

The authentication system includes temporary account lockout protection.

After multiple failed login attempts, the account is temporarily blocked to reduce the effectiveness of brute-force attacks.

---

## 👥 Role-Based Access Control

FalconSigned implements Role-Based Access Control (RBAC) with four roles.

| Role | Main Responsibility |
|---|---|
| **Administrator** | User management, key management, document revocation, signing and verification |
| **Signer** | Document signing and verification |
| **Verifier** | Document verification |
| **Auditor** | Independent security audit review |

### Separation of Duties

FalconSigned separates administrative and auditing responsibilities.

The **Administrator cannot access the security audit log**.

The **Auditor** is an independent role dedicated to reviewing security events and cannot:

- Sign documents
- Create users
- Rotate cryptographic keys
- Revoke cryptographic keys
- Revoke documents

Only one active auditor account is permitted by the current prototype.

This design demonstrates the cybersecurity principle of **Separation of Duties (SoD)**.

---

## 🔑 Cryptographic Key Management

FalconSigned manages the lifecycle of RSA cryptographic keys.

Supported operations include:

### Key Generation

RSA key pairs are automatically generated by the system.

### Private Key Protection

Private RSA keys are encrypted using a master vault password before being stored locally.

### Key Rotation

Administrators can rotate the active RSA key.

The previous key becomes retired while a new key becomes active for future signatures.

Historical public keys remain available so previously signed documents can still be verified.

### Key Revocation

If a private key is suspected of being compromised, the administrator can revoke it.

Documents previously signed with that key can still be mathematically verified, but FalconSigned warns that the key has been revoked and the document should no longer be considered trusted.

---

## 📄 Document Revocation

FalconSigned supports administrative document revocation.

A revoked document is not deleted from the system.

Instead, its status changes so that the cryptographic evidence and historical information remain available while the document is no longer considered valid.

---

## 🆔 FALCON Document Codes

Each registered document receives a unique identifier similar to:

```text
FALCON-2026-00001
```

The FALCON code is used to locate the document record during verification and recovery.

> The FALCON code itself is **not proof of authenticity**.

Document authenticity depends on the SHA-256 integrity check, RSA-PSS digital signature, cryptographic key status, and document status.

Copying a FALCON code to a forged document does not produce a valid signature.

## 📋 Security Auditing

FalconSigned maintains an audit log containing relevant security events.

Examples include:

```text
LOGIN_EXITOSO
LOGIN_FALLIDO
FIRMA_DOCUMENTO
VERIFICACION_EXITOSA
VERIFICACION_FALLIDA
ROTACION_CLAVE
REVOCACION_CLAVE
REVOCACION_DOCUMENTO
DESCIFRADO_DOCUMENTO
```

Audit records contain information such as:

- Timestamp
- User
- Action
- Event details

Audit log access is restricted to the **Auditor** role.

## 🚀 Initial Setup

On the first execution, FalconSigned automatically starts the initial configuration process.

The application will request:

1. Initial administrator username
2. Administrator password
3. Master vault password
4. Initial RSA key generation
5. MFA configuration

The generated MFA secret can be configured in a compatible TOTP authenticator application.

## 🧪 Security Tests

The prototype can be tested using scenarios such as:

| Security Test | Expected Result |
|---|---|
| Incorrect password | Access denied |
| Incorrect MFA code | Access denied |
| Multiple failed login attempts | Temporary account lockout |
| Verify original signed PDF | Valid signature |
| Modify signed PDF | Integrity verification fails |
| Rotate RSA key | New key becomes active |

| Revoke RSA key | Document is flagged as untrusted |
| Revoke document | Document is reported as revoked |
| Administrator attempts audit access | Access denied |
| Auditor accesses audit log | Access allowed |
| Auditor attempts signing operation | Access denied |
| Correct vault password used for recovery | Encrypted PDF can be recovered |

## ⚠️ Project Limitations

FalconSigned is an academic proof of concept and currently has several limitations:

- It operates locally and is not a network service.
- It does not implement a centralized server architecture.
- It does not integrate with an external Certificate Authority (CA).
- It does not issue X.509 certificates.
- It does not implement a complete Public Key Infrastructure (PKI).
- It does not provide cloud synchronization.
- Backups must currently be performed externally.
- Local machine security remains important for protecting application data.
- It is not intended to replace legally certified digital signature solutions.

These limitations provide opportunities for future development.
